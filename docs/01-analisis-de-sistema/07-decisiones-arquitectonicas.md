# Decisiones arquitectónicas

| ID | Decisión arquitectónica | Driver relacionado | Justificación | Alternativas descartadas | Resultado |
|---|---|---|---|---|---|
| ADR-001 | **Monolito modular para el backend** | DA01 – HCE como núcleo; DA04 – Desarrollo individual y bajo costo; DA08 – Mantenibilidad | Organizar las funcionalidades en módulos independientes dentro de una sola aplicación desplegable, que una sola persona puede desarrollar, desplegar y operar con bajo costo, manteniendo límites claros entre módulos. | Microservicios: exigen desplegar, monitorear y comunicar muchos servicios, lo que no es viable para una sola persona ni para el presupuesto. Los límites entre módulos permiten separarlos en el futuro si se requiere. | Una API en C# / .NET con los módulos Admisión y Triaje, HCE, Farmacia, Laboratorio, Reportes y Alertas, Administración y Notificaciones. |
| ADR-002 | **Clean Architecture dentro de cada módulo** | DA08 – Mantenibilidad; DA09 – Servicio externo APIPERU | Separar las reglas del negocio clínico de los detalles tecnológicos (base de datos, caché, servicios externos), para que cada módulo pueda especificarse y generarse con SDD de forma ordenada. | Arquitectura en capas tradicional sin inversión de dependencias: acopla las reglas del negocio a la base de datos. | Capas de Dominio, Aplicación, Infraestructura y Presentación (API REST) en cada módulo. |
| ADR-003 | **Frontend en React como aplicación de una sola página (SPA)** | DA10 – Aplicación web y API REST | Separar la interfaz del backend y consumir la API REST; React tiene amplio soporte, abundante documentación y buena generación de código con IA. | Angular: mayor curva de aprendizaje. Blazor: no cubrió las expectativas del autor en experiencias previas. | Aplicación web en React que consume la API REST del backend. |
| ADR-004 | **Separación física OLTP / OLAP con ETL programado** | DA03 – Aislamiento de cargas; DA04 – Bajo costo | Evitar que los reportes, dashboards y alertas degraden la operación clínica, usando PostgreSQL para ambos almacenes pero en esquemas o instancias separadas, y un ETL en Python programado con cron. | SSAS o Apache Kylin: costosos o pesados. Consultas analíticas directas sobre la base transaccional: afectan el rendimiento clínico. Apache Airflow: requiere más infraestructura de la necesaria. | Base transaccional (OLTP) y datamart analítico (OLAP) separados, con vistas materializadas agregadas y un proceso ETL periódico. |
| ADR-005 | **Alerta epidemiológica como proceso independiente** | DA03 – Aislamiento de cargas; DA08 – Mantenibilidad | Ejecutar el análisis de alertas fuera de la API principal, leyendo solo el datamart, para que una falla o la desactivación del módulo no afecte al resto del sistema. | Implementarlo dentro de la API transaccional: compite por recursos con la operación clínica y acopla el módulo al resto. | Proceso en Python programado que analiza el datamart y registra las alertas, que la API expone al epidemiólogo para su revisión. |
| ADR-006 | **Caché con Redis** | DA05 – Rendimiento; DA07 – Escalabilidad | Reducir consultas repetitivas a la base de datos (catálogos CIE-10, medicamentos, exámenes, datos frecuentes del paciente) y mantener la API sin estado. | Caché en memoria de la propia aplicación: se pierde al reiniciar y no se comparte entre instancias. | Una instancia Redis en contenedor como caché compartida. |
| ADR-007 | **Autenticación con JWT, autorización por rol y registro de auditoría** | DA02 – Seguridad; DA07 – Escalabilidad | Proteger la información clínica, restringir cada funcionalidad según el rol del usuario y registrar cada acceso y modificación a la historia clínica. JWT no requiere guardar sesiones en el servidor. | Sesiones en el servidor: dificultan el escalamiento horizontal. | Tokens JWT, control de acceso basado en roles (RBAC), TLS obligatorio y una bitácora de auditoría de accesos a la HCE. |
| ADR-008 | **Registros clínicos inmutables** | DA02 – Seguridad (integridad) | Una historia clínica es un documento legal: los registros firmados no se modifican ni eliminan, y las correcciones se guardan como notas adicionales vinculadas al registro original. | Permitir editar o eliminar registros: rompe la integridad y la trazabilidad exigidas por la normativa. | Modelo de datos de solo inserción para registros clínicos firmados, con notas de corrección. |
| ADR-009 | **Integración con APIPERU mediante interfaz, adaptador y Circuit Breaker** | DA09 – Servicio externo APIPERU; DA06 – Disponibilidad | Los casos de uso dependen del contrato `IServicioIdentidad` y no de APIPERU. El adaptador `AdaptadorApiPeru` traduce la llamada al formato del servicio, con un tiempo de espera corto y un Circuit Breaker: tras varias fallas seguidas deja de llamar a APIPERU por un tiempo y el sistema pasa directamente al registro manual (RF02). Antes de consultar, se busca si el paciente ya está registrado (RF03), para no gastar consultas del plan. | Llamar a APIPERU directamente desde los casos de uso: acopla la lógica al proveedor. Reintentar sin límite: bloquea la admisión y agota el límite del plan. | Contrato `IServicioIdentidad`, `AdaptadorApiPeru` para producción y `AdaptadorIdentidadSimulado` solo para pruebas automatizadas (sin consumir el plan), Circuit Breaker y registro manual de contingencia. |
| ADR-010 | **Despliegue en contenedores con Docker Compose en AWS** | DA04 – Bajo costo; DA06 – Disponibilidad; DA07 – Escalabilidad | Empaquetar cada servicio en un contenedor con healthchecks y reinicio automático, desplegados en una o dos instancias EC2, con backups automáticos en S3. Los contenedores son portables a Kubernetes si se escala. | Kubernetes: costoso y complejo de operar para una sola persona. Servidores dedicados por capa: costo elevado. | Docker Compose con `restart: always` y healthchecks, en EC2, con backups en S3 (snapshots + WAL). |
| ADR-011 | **Metabase como herramienta de BI** | DA03 – Aislamiento de cargas; DA04 – Bajo costo | Ofrecer dashboards y reportes interactivos conectados solo al datamart, con una herramienta gratuita, liviana y fácil de configurar para una sola persona. | Power BI: requiere licencia. Apache Superset: más potente pero más pesado de instalar y configurar. | Metabase en contenedor, conectado al datamart analítico. |
| ADR-012 | **Gestión de secretos con variables de entorno** | DA09 – Servicio externo APIPERU; DA02 – Seguridad | El repositorio es público (RC18). Las credenciales se leen desde variables de entorno: en desarrollo, desde un archivo `.env` ignorado por Git; en el servidor, desde el entorno de Docker Compose. .NET las lee con la convención `ApiPeru__Token`. El repositorio solo incluye `.env.example`, con los nombres de las variables y los valores vacíos. | Guardar el token en `appsettings.json` o en el código: quedaría expuesto en GitHub. Un gestor de secretos administrado (por ejemplo, AWS Secrets Manager): agrega costo y complejidad; queda como mejora si el sistema escala. | `.gitignore`, `.env.example` y configuración por entorno. Si una clave llega a exponerse, se revoca y se genera una nueva en el proveedor. |
| ADR-013 | **Notificaciones push con el estándar Web Push (VAPID)** | DA11 – Notificaciones; DA04 – Bajo costo | Web Push es un estándar de los navegadores: es gratuito, no requiere una cuenta en un proveedor externo y avisa aunque la aplicación esté cerrada. La aplicación React registra un Service Worker; la suscripción de cada usuario se guarda en `sigh_oltp`, y el backend firma los mensajes con las claves VAPID, guardadas como secretos (ADR-012). | Firebase Cloud Messaging: requiere cuenta y SDK de un proveedor externo y más configuración. Solo SignalR o WebSockets: avisan únicamente con la aplicación abierta. Correo o SMS: más lentos o con costo por mensaje. | Service Worker en la aplicación web, suscripciones por usuario y envío desde el backend con una librería Web Push para .NET. |
| ADR-014 | **Módulo de Notificaciones transversal basado en eventos de dominio** | DA11 – Notificaciones; DA08 – Mantenibilidad | Los módulos publican eventos de dominio (por ejemplo, `ResultadoLaboratorioRegistrado`) sin saber quién los atiende (patrón Observer). El módulo de Notificaciones decide a qué roles avisar, arma un mensaje sin datos clínicos (RC19), lo guarda en la bandeja interna y lo envía en segundo plano, de modo que una falla del envío nunca detiene el registro clínico. La alerta epidemiológica, que corre fuera de la API, avisa mediante un endpoint interno protegido. | Que cada módulo envíe sus propias notificaciones: duplica código y acopla todos los módulos a Web Push. Enviar dentro de la misma operación clínica: si el servicio push falla o tarda, el registro clínico se demora o falla. | Módulo `Sigh.Notificaciones` con manejadores de eventos, cola de envío en segundo plano y bandeja interna (RF25 a RF27). |
